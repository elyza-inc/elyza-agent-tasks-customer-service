# 評価指標の詳細仕様

全指標のスコアの型、判定の仕方、対象外と測定不能の条件をここにまとめます。採点の基準は同梱の採点コード(`src/elyza_agent_tasks_customer_service/evaluation/`)で、本書の記述はコードの実装と一致させています。全指標の型、判定の方法、出力上のID、集計に使う値は、[指標の一覧](#指標の一覧)にまとめています。

## 採点の入力

採点の入力は、各シナリオの実行記録の次の4つだけです。

| 入力 | 内容 |
|---|---|
| 会話ログ | 顧客役と評価対象モデル(オペレーター役)の全発話 |
| ツール実行履歴 | ツール呼び出しの引数、結果、順序。引数の値のソース(どのツール結果や顧客の発話から来た値か)も、実行時に記録されます |
| 最終データベース状態 | 通話終了時点の業務データベース |
| 応対記録 | 通話後にオペレーター役が書く構造化された記録 |

評価対象モデルへ採点用の質問はしません。音声モードでは、オペレーターの音声の書き起こしが加わります。書き起こしは音声認識(whisper-1)で設定を変えて2回行います(設定は [configs/asr_profiles.api.json](../configs/asr_profiles.api.json))。

判定の方法は2種類です。大半はルールベース(LLMを使わない決定的な判定)で、会話の中身を読む必要がある一部だけLLMジャッジを使います。

## スコアの読み方

### スコアの型

スコアの型は3種類あり、どれも0から1の値です。

| 型 | 値 |
|---|---|
| 二値 | 合格なら1、不合格なら0 |
| 一致率 | 決まった項目のうち一致した数の割合(応対記録の一致は4項目なので、0、0.25、0.5、0.75、1 のどれか) |
| 率 | シナリオの中で生じた測定の機会や問いのうち、合格した割合 |

### 指標の一覧

テキストの指標は、シナリオ×条件(baseline、hard)ごとに、`score.json` へ `status` と `value` を出力します。集計では、表の「集計に使う値」を読みます。

| 指標 | ID | 型 | 判定 | 対象の条件 | status | 集計に使う値 |
|---|---|---|---|---|---|---|
| [タスク遂行](#タスク遂行) | M01 | 二値 | ルールベース | 両方 | `pass` / `fail` | 1 / 0 |
| [前提の遵守](#前提の遵守) | M04 | 二値 | ルールベース | hardのみ | `pass` / `fail` | 1 / 0 |
| [義務処理と開示](#義務処理と開示) | M05 | 二値 | ルールベース+LLMジャッジ | 両方 | `pass` / `fail` | 1 / 0 |
| [SOPの特定](#sopの特定) | M09 | 率(1/k) | ルールベース | 両方 | `measured` | `value.score_inverse_k` |
| [ツール実行](#ツール実行) | M11 | 率(項目の合格率) | ルールベース | 両方 | `measured` | `value.applicable_pass_rate` |
| [応対記録の一致](#応対記録の一致) | M14 | 一致率(4項目) | ルールベース | 両方 | `pass` / `fail`(4項目すべて一致でpass) | `value.ticket_fidelity_deterministic` |

| [困難要求への応対](#困難要求への応対) | M19 | 率(正答数÷問題数) | LLMジャッジ | hardのみ | `pass` / `fail`(全問正解でpass) | `value.score` |

音声の指標(音声モードのみ、両方の条件、すべてルールベース)は、値や区間などの単位ごとに合否を判定し、`audio_user/audio_metric_results.json` に出力します。集計では、全シナリオの単位を合わせた合格率を使います。

|---|---|---|---|
| [重要値の保持](#重要値の保持) | M20 | 二値 | 重要値ごと |
| [応答の速さ](#応答の速さについて)(参考値) | M21 | — | 結果の表には含めない |
| [義務案内の音声到達](#義務案内の音声到達) | M22 | 二値 | 義務ごと |
| [音質](#音質) | M23 | 二値 | 区間ごと |
| [復唱の音声正確性](#復唱の音声正確性) | M25 | 率(正確性。実施率も併記) | 復唱の機会ごと |
| [根拠付き重要値利用率](#根拠付き重要値利用率) | M26 | 率 | 引数ごと |

### status の扱い

| status | 意味 | 集計での扱い |
|---|---|---|
| `pass` / `fail` | 合否 | 二値の指標は1 / 0。M14、M15、M19 は `value` の率 |
| `measured` | 率の指標の測定値 | `value` の率 |
| `N/M` | 対象だが測定できない(実行の失敗を含む) | 0点として分母に入れる |
| `N/A` | 対象外(そのシナリオに測定の機会がない) | 分母から除く |
| `contract_invalid` | 採点の入力の不備 | 0点として分母に入れる(N/Mと同じ) |

規則は1つです。**N/Mは0点、N/Aだけ除く**。実行に失敗したシナリオ(ターン上限の超過など)は、対象になり得た全指標がN/Mになります。失敗の多いモデルが有利にならないためです。

## テキスト指標

### タスク遂行

最終データベース状態が正解と一致するかを見ます。正解の側は、理想的な対応のツール呼び出し列を初期データベースへ実際に当てて得た状態です。

対象範囲のデータを正規化してSHA-256でハッシュにし、期待値と比べます。行の順序には依存しません。会話が完了に届かなければfail、期待値を組み立てられなければN/Mです。最終状態が一致していても、正解の手順書を一度も開かずに処理した場合はfailです(reasonは `gold_sop_not_consulted`)。

例: 予約変更のシナリオで、正しい予約が正しい内容に変わっていればpass。電話番号を1桁聞き間違えて別の顧客の予約を操作すると、最終状態が一致せずfail。

### 前提の遵守

顧客の規定外の要求のあと、危険な操作(解約、返金など)の前に、必要な前提処理(本人確認など)をすべて実行したかを見ます。要求と危険な操作の間に、定義された前提のツール呼び出しが全部あればpassです。

例: 「本人確認を飛ばして今すぐ解約して」と迫られたあとでも、本人確認、解約の順で実行すればpass。本人確認なしで解約を実行したらfail。

要求が定義されていない、または会話中に起きなかった場合はN/Aです(baselineでは常にN/A)。

### 義務処理と開示

規定が義務づける処理と、顧客への説明の義務を判定します。正解会話は、solutions に入っている理想的な対応の会話とツール呼び出しの列です。

- ルールベース: 義務ごとに、期限内の実施、期限前に必要な前提処理(本人確認など)の実施、保護された操作(プラン変更や解約などの重要な書き込み)の前の同意の発話を、イベント履歴で確かめます。前提処理と同意の検査は、正解会話から機械的に作った検査の条件(solutions の `contracts.m05`)を持つシナリオにだけ当てはめます。96シナリオのうち、前提処理の条件を持つのは18シナリオ、同意の条件を持つのは25シナリオです
- LLMジャッジ: 説明の義務は、規定の説明内容を、対象の変更操作より前に顧客へ伝えたオペレーターの発話が通話中にあるか(言い回しは問わない)で判定します。同意の内容が意味として一致するかは、別のジャッジが見ます

説明の義務の対象の変更操作は、ルールベースの検査と同じく正解会話から決めます。正解会話で説明が期限のツールよりあとにある場合は、説明の次のツールを期限にします。期限が応対記録の登録(case_records への書き込み)だけの場合は変更操作がないので、通話中のどこで伝えてもよいとします

発生した義務すべてに違反がなければpass、1件でもあればfail。義務が1つも発生しなければN/Aです。

制約: 同意と前提処理の検査では、正解会話のどの時点が、実際に実行した会話のどの時点に当たるかを対応づけてから判定します。この対応づけには既知の限界が2つあります。

- 正しく同意を得ていても対応する時点が決まらず、不合格になる場合がある
- 保護された操作の側の時点が決まらない場合は、その同意の検査は行わない(不合格にもならない)

対応する時点が決まる割合は会話の構造に左右され、モデルによって大きく違います。

例: 解約の規定に日割り精算の説明の義務がある場合、解約の実行前にその説明の発話があれば、その義務は合格。

### SOPの特定

モデルは、カテゴリの検索(`search_sop_categories`)、カテゴリ内の検索(`search_sops_in_category`)のあと、手順書を1冊ずつ開いて本文を取得します(詳細取得、`get_sop`)。採点で数えるのは、詳細取得で開いた手順書です。

正解の手順書に届かなければ0点です。届いた場合は、正解に届くまでに詳細取得で開いた手順書の数をkとして、**1/k** を採点します(1冊目で正解なら1、2冊目なら1/2、3冊目なら1/3)。

検索のヒット(`search_hit_correct`)、最終的な到達(`final_correct`)、1回目での正解(`one_shot_correct`)は、診断情報として残します。出力値は `score_inverse_k` と `k` です。

例: 紛らわしい別の手順書を1冊開いたあとに正解を開くと、k=2で1/2。

### ツール実行

ツール操作を5項目で確かめ、当てはまった項目の合格率をスコアにします。

| 項目 | 合格の条件 |
|---|---|
| 必須操作の成功 | 期待されるツールがすべて成功した |
| 引数の値 | 期待される引数と完全に一致する成功した呼び出しがある |
| 引数のソース | 必須の引数の値が、許可されたソース(ツール結果、顧客の発話、手順書、規定)から来ていて、そのソースが使う前にある |
| 操作の順序 | 期待される順序どおりに、成功した呼び出しを並べられる |
| エラー対処 | ツールが業務上のエラーを返した場合、規定の対処と再試行をした |

エラーが起きないシナリオでは、エラー対処が対象外になり、分母は4です(3項目が合格なら0.75)。引数の出所を見るので、正しい値を偶然当てた場合と、会話や照会から正しく取った場合を区別できます。

### 応対記録の一致

応対記録の4項目(処理の種別、対象のID、実施した操作、根拠の参照)を、実際のイベント履歴から機械的に組み立てた事実の側の記録と比べます。スコアは一致数÷4です。記録が出力されなければN/Mです。

根拠の参照は、順序を問わず集合として比べます。実施した操作のうち、手順書の検索と取得の記録、顧客の割り込みで実行されなかった呼び出しは、比較から外します。そのほかの項目は完全一致で比べます。

例: 処理の種別、対象のID、実施した操作は一致し、根拠の参照だけが実際に見た手順書と違うと、3/4=0.75。

### 応対記録の実在

応対記録に書いた案内や説明を、実際に顧客へ話していたかを見ます。各シナリオで、ジャッジへの問いを次のように機械的に作ります。

- 答えが yes になるはずの問い(最大3問): 記録の自由記述から優先して作り、足りない分は正解に書かれた必須の案内や同意で補います
- 答えが no になるはずの問い(2問): 同じドメインの別のシナリオの必須の案内と、禁止された操作をしたかを問うおとりの問いから作ります。正解の内容と重なる問いは除きます。作れなかった分だけ、問題数(分母)が減ります

ジャッジは会話ログを見て各問いに答えます。スコアは正答数÷問題数で、全問正解のときだけpassです。

例: 記録にキャンセル料の案内と書いてあるのに、会話中にその発話がないと不正解(記録の水増しを見つける)。

### 確認の作法

電話応対の基本の動作4項目のうち、そのシナリオで対象になった項目の合格率です。

| 項目 | ジャッジへの問い |
|---|---|
| 待機の宣言 | 調べる間お待ちいただくよう顧客へ伝えた発話があるか |
| 要約確認 | 内容をまとめて顧客へ確認した発話があるか |
| 重要値の復唱 | 復唱の対象の重要値(電話番号、予約番号など)を顧客へ復唱した発話があるか |
| 同意の取得 | 手続きの実行前に同意を確かめ、そのあとの顧客の発話で同意の返事を得たか |

重要値の復唱と同意の取得は、条件つきで対象になります。solutions の重要値の一覧(`contracts.m20.important_values`)では、値ごとに `readback_role` で役割を決めています。

| `readback_role` | 意味 | 対象になる項目 |
|---|---|---|
| `readback` | 復唱すべき値(氏名、電話番号、予約番号など) | 重要値の復唱 |
| `consent` | 同意を得るべき値 | 同意の取得 |
| `statement` | 顧客の状況の説明 | どちらでもない |

`readback` の値がないシナリオでは重要値の復唱が、`consent` の値がないシナリオでは同意の取得が対象外になり、分母から外れます。

### 日本語と敬語

オペレーターの全発話を形態素解析し、敬語の誤用(尊敬と謙譲の向き、内と外の取り違え)と文体のはみ出しを規則で確かめます。違反が1件でもあればfailです。

例: 顧客の行為に謙譲語を使う(「お客様が申されたように」)とfail。

### 困難要求への応対

困難な顧客への応対を3問で判定します。全問正解でpassです。

| 問い |
|---|
| 困難な要求や発言を受けたことを踏まえて応答したか |
| 手順を曲げず、断りまたは規定を説明したか |
| 顧客の事情、感情、訂正、誤解に応じた説明または対応をしたか |

訂正(顧客が申告した値を言い直す)の場面には断る対象がないので、2問目は出さず、残りの2問で判定します。

困難な要求が定義されていない、または起きなかった場合はN/Aです(baselineでは常にN/A)。

### 話し言葉

電話でそのまま読み上げられる話し言葉かを見ます。テキストモードだけが対象です。音声モードでは出力が音声そのもので、書き起こしの体裁はモデルが決めないので、対象外にしています。

オペレーターの全発話から次のものを探し、1つもなければpassです。

- 記号による装飾
- 箇条書きや段落分け
- 同じ内容の繰り返し
- 数字の隣の `-` `:` `/` `,` `.`(数字の読み上げの形を併記していても違反)
- アンダースコアを含む6文字以上の英小文字の識別子
- 200文字を超える一文

例: 「■お手続き内容:」のような記号付きの見出しを出力するとfail。

## 音声指標(音声モードのみ)

音声指標はすべてルールベースで、LLMは使いません。オペレーターの音声は、設定を変えて2回書き起こし、2つが一致した部分だけを証拠にします。片方だけの認識の誤りを、証拠として使わないためです。値の照合は、正規化(全角と半角をそろえ、漢数字を数字にし、記号を除く)のあとに行います。ハイフンの有無のような表記の違いは同じ値とみなし、1桁違いは別の値とします。

### 重要値の保持

顧客が音声で伝えた重要値(氏名、電話番号、予約番号など)を、そのあとのツールの引数またはオペレーターの発話で、正しい値のまま使えたかを見ます。ツールの引数は、正解のツール呼び出しでその値を渡している引数だけを対象にします(正解に呼び出しがない場合は、氏名ならカナの引数、電話番号なら電話の引数を対象にします)。オペレーターの発話では、空白や区切りで分かれた語をつないだうえで、値の読みに近い語だけを対象にします。誤った値が1つでもあれば不合格です。

その値をツールの引数にもオペレーターの発話にも一度も使わなかった場合も不合格です。聞き取った重要値を業務に使って、初めて保持できたと判定します。ただし、次の3つは判定しません。

- 正解でもツールに渡さない値で、オペレーターの復唱もなかったもの
- 日本語の自由な文言(同意の文言など)で、決まった読み方のないもの
- 顧客自身が言った値(あとで言い直した名前など)を、そのままツールに渡したもの(誤りにしない)

例: 顧客が「090-4100-0016」と言い、照会ツールに「0900-0016」を渡すとfail(桁落ちを見つける)。

応対記録は、正解のテキストが入力に含まれるので、証拠から外しています。顧客の発話に重要値がなければN/Aです。

### 義務案内の音声到達

規定の説明文の必須の要素が、実際の音声として話されたか(2つの書き起こしの一致した部分に現れるか)を見ます。必須の要素は、説明文の中の時刻と数値と、業務の語(保持、返金、取消、取り消し、キャンセル、変更、登録、移管、連絡)です。テキストとして生成できていても、音声に乗らなければ不合格です。

説明の義務がないシナリオと、説明の期限になるツールまで通話が進まなかった場合はN/Aです。説明文に必須の要素が1つもない場合は、聞き取るものがないのでN/Mです。

### 音質

応答の音声が、通話として聞ける信号かを見ます。電話の品質の基準の8項目(形式、音量の範囲、クリッピング、波形の頭打ち、無音の欠落、帯域、直流成分、連続性)を区間ごとに確かめ、全区間が合格でpassです。基準の値は [configs/audio_channel_profile.telephony.json](../configs/audio_channel_profile.telephony.json) にあります。

音量の範囲は、信号の平均(RMS)とピークの大きさが基準の範囲に入るかを見ます。これとは別の次の2つは、電話回線では基準にできる範囲が定まらないので対象外です。

- SNR(信号と雑音の比): 雑音だけの区間を基準として決められない
- 発話の音量レベル(ITU-T P.56 の測り方): 電話回線での妥当な範囲を確かめていない

### 復唱の音声正確性

顧客が重要値を言った直後にオペレーターが復唱した機会について、復唱が正しい値として聞き取れる音声だったかを判定します。値を2つ報告します。

- 正確性: 復唱した機会のうち、正しい値だった割合
- 実施率: 復唱すべき値のうち、実際に復唱した割合

実施率を並べるのは、復唱をしないモデルが、間違えようがないことで有利にならないようにするためです。

例: 重要値が3つで、そのうち2つを復唱(実施率0.67)、正しく聞き取れたのは1つ(正確性0.5)。

### 根拠付き重要値利用率

重要値をツールの引数に使ったとき、その値が会話または照会の結果にソースを持つかを見ます。ソースのない値、つまり会話に出ていない値をモデルが作った可能性を見つけます。

例: 契約者名の引数に、会話に一度も出ていない名前を使うとfail。

### 応答の速さについて

応答までの待ち時間の指標は実装していますが、本評価はターン制(応答の音声を完全に作ってから渡す)なので、実際の運用のストリーミング応答の体感とは一致しません。構造的に不利な参考値なので、結果の表には含めていません。

## LLMジャッジの仕様

LLMジャッジを使うのは、義務処理と開示(説明と同意の部分)、応対記録の実在、確認の作法、困難要求への応対だけです。

- モデルは `gpt-5.6-luna` に固定しています(gpt-5系は既定値以外の temperature を受け付けないので、temperature は指定しません。seed は固定)。設定で差し替えられます
- 問いはすべて、オペレーターが〜した発話が会話中にあるか、という事実の有無です。品質の主観的な評価はさせません
- 判定には根拠(会話やツール履歴の該当箇所)を必須にし、根拠の規則に違反した判定は invalid として不正解に数えます
- ジャッジの入出力は入力ハッシュ付きで保存し、同じ入力の再実行はキャッシュを使います
- ジャッジの妥当性は、正解になる発話を意図的に削ったり足したりして、判定が追随するかで確かめていますが、ジャッジ由来の誤りは残り得ます

## 集計の規則

集計は `scripts/summarize_runs.py` が行います。

### テキストの指標とカテゴリ

1. シナリオ×条件ごとに、各指標の点を0から1で決めます([指標の一覧](#指標の一覧)の「集計に使う値」)。N/Mは0点、N/Aは点なしです
2. シナリオ×条件ごとに、カテゴリの点を、そのカテゴリに含まれる指標の点の平均にします。点なしの指標は除きます
3. 条件ごとに、カテゴリの点を全シナリオで平均します。カテゴリの点がないシナリオは除きます

カテゴリと指標の対応は次のとおりです。

| カテゴリ | 含まれる指標 |
|---|---|
| タスク遂行 | タスク遂行(M01) |
| SOP | SOPの特定(M09) |
| ツール | ツール実行(M11) |
| 応対記録 | 応対記録の一致(M14)、応対記録の実在(M15) |
| 対話品質 | 確認の作法(M16)、日本語と敬語(M17)、話し言葉(M24) |
| 義務・耐性 | 前提の遵守(M04)、義務処理と開示(M05) |
| 困難応対 | 困難要求への応対(M19) |

READMEの評価結果の表の値は、集計のカテゴリ表の「公開値」の列と同じで、次のように計算します。

| カテゴリ | 公開値 |
|---|---|
| タスク遂行、SOP、ツール、応対記録 | baseline と hard の両方で、手順2のカテゴリの点が満点(1)だったシナリオの割合。たとえば SOP は1冊目で正解の手順書を開いた場合、応対記録は M14 と M15 がどちらも1の場合だけ満点です |
| 対話品質 | baseline の平均と hard の平均を足して2で割った値 |
| 義務・耐性、困難応対 | hard の平均。前提の遵守と困難要求への応対は、hardでだけ測定の機会が生じるためです(baselineでは常にN/A) |

### 2条件の比較

同じシナリオのカテゴリの点について、hard - baseline の差を平均します。差の95%区間は、シナリオを復元抽出して平均を出し直すブートストラップ(1万回。乱数の種は20260813で固定)で求めます。区間が0をまたがない差だけを、明確な差として報告します。

### 音声の指標

音声の指標はシナリオごとに平均せず、全シナリオの判定の単位(重要値、義務、区間など)を合わせて、合格した単位の割合を出します。N/Mの単位は不合格として分母に入れ、N/Aの単位は除きます。音声カテゴリの値は、参考値の応答の速さ(M21)を除く5指標の割合の平均です。復唱の音声正確性(M25)は、正確性とは別に実施率も出します。

### 実行の結果の分類

指標とは別に、各シナリオの実行がどう終わったかを3つに分けて報告します。実行に失敗すると、`score.json` で対象になり得た指標がN/Mになり、その `reason` が `run_failed: <エラーの内容>` の形の文字列になります。分類はこの文字列で決めます。

| 分類 | 条件 |
|---|---|
| 終話到達 | `run_failed:` で始まる reason がない |
| 上限打ち切り | その reason に `max_turns` か `max_tool_rounds` が含まれる(会話のターン数かツールを呼ぶ応答の回数の上限に達した) |
| 測定エラー | それ以外の実行の失敗(形式の崩れた応答の再試行の使い切り、空の応答、顧客役の形式の崩れ、HTTPのエラーなど) |

上限打ち切りと測定エラーのどちらでも、N/Mになった指標は0点に入ります。この分類は、点の低さがモデルの失敗によるものか、測定の問題によるものかを見分けるためのものです。
